CHAPTER 3. METHODOLOGY (PROPOSAL DESIGN)
3.1. System Architecture 
3.1.1. Frontend Design and Client-side Interaction
The user interface of the Vựa Vui Vẻ system is currently developed using HTML and CSS combined with vanilla JavaScript. The frontend is organized as a set of static pages with event-driven interactions. Main shopping pages are implemented in HTML, while browser-side logic is separated into JavaScript modules responsible for functions such as cart management, product display, recommendation rendering, and order handling. User authentication and basic account management are handled on the client side. The frontend communicates with the backend through RESTful APIs using the HTTP/JSON format to retrieve product and order data, update cart contents, and synchronize order status.
From a user experience perspective, the interface applies several lightweight optimization techniques to ensure smooth interaction. These include lazy-loading for product images, “toast” notifications for user feedback, and responsive event handling for actions such as “Thêm vào giỏ”. Session data and shopping cart information can be stored locally on the client to reduce unnecessary API requests and maintain a continuous and user-friendly shopping experience.
The recommendation functionality on the frontend is implemented through two complementary approaches. Seasonal recommendations are handled by the season.js module, where the seasonal page requests data from the /api/recommend/seasonal endpoint to display “combo mua kèm theo mùa”. In cases where seasonal data is insufficient, the system automatically falls back to popularity-based recommendations to preserve usefulness. Personalized recommendations are managed by the recommended.js module, which applies lightweight heuristics by filtering user order history, aggregating purchase frequencies across products, categories, and groups, and ranking the results into three sections: “Mua lại nhanh”, “Tương tự”, and “Xu hướng”. Both recommendation modules are tightly integrated with user interaction events, such as the “Thêm vào giỏ” button, with a strong emphasis on performance and simplicity to match the current data scale and project scope.
Although the current implementation does not yet use React, the frontend architecture is designed to support a gradual migration to a React-based Single Page Application (SPA). Existing HTML pages can be refactored into reusable components, and JavaScript logic can be reorganized into hooks or service layers, while SPA routing can replace static page navigation. This transition would preserve the existing REST API structure and allow easier integration of state management libraries such as Redux or Zustand for handling the shopping cart, user sessions, and recommendation data. Overall, the planned upgrade path ensures technical scalability while minimizing disruption to both backend implementation and user experience.
3.1.2. Backend Architecture and Business Logic Handling
The backend layer of the Vựa Vui Vẻ system is implemented using Node.js and is responsible for handling application logic and API services. The primary backend setup is built on JSON Server combined with custom middleware modules to support business logic processing. The main entry point of this backend route is server-simple.js. Custom middleware defined in server-middleware.js manages inventory deduction and restoration during order creation and updates, synchronizes product data to storage files, and ensures data consistency across different order states such as order placement, successful delivery, and cancellation or return.
In addition to standard REST resources such as /products, /orders, and /users, the backend exposes several business-specific endpoints. These include /api/orders/:id/paid and /api/orders/:id/payment-failed, which are used to receive payment results from VNPay and update inventory levels and order statuses accordingly. The endpoint /api/recommend/:userId provides time-aware personalized recommendations generated by the Time-Aware CF module, while /api/recommend/seasonal returns seasonal product bundles based on the S-Apriori algorithm. A proxy endpoint /proxy/rss is also implemented to support CORS handling when retrieving RSS content for the news section. This modular architecture allows new middleware or endpoints to be added without disrupting the core CRUD workflow.
In parallel with the JSON Server-based backend, the project also provides an alternative API implementation using Express through server.js. This route utilizes a centralized data management component defined in dataManager.js to perform CRUD operations for products, orders, users, and audit logs in a consistent manner. All system data is stored in JSON files within the data directory, which supports rapid development, testing, and offline analysis. The data manager also exposes basic statistical APIs, including dashboard summaries, monthly revenue reports, and top-selling product lists, as well as action logging through audit logs. This structure enables backoffice monitoring without relying on an external database system.
Payment integration with VNPay is implemented as a separate Node.js application located in the vnpay_nodejs module, configured using sandbox settings in default.json. After users complete or cancel a transaction, the interface redirects to vnpay-return.html, which triggers the corresponding backend endpoints (/api/orders/:id/paid for successful payments or /api/orders/:id/payment-failed for failed transactions). This separated design ensures a clear and secure payment workflow, where order status transitions (paid/failed/cancelled) are handled on the backend, and inventory is only deducted after payment confirmation. As a result, the system avoids data inconsistencies in cases of cancelled or failed transactions.
3.1.3. Machine Learning Engine and Recommendation Modules
The Recommended Page uses a fusion recommendation approach that incorporates three different machine learning algorithms to provide tailored suggestions to customers. The RWB website uses Matrix Factorization with Singular Value Decomposition (SVD) to identify hidden relationships between customers and products, Apriori Association Rule Learning to identify customers who "Bought Together Frequently," and Content-Based Filter with TF-IDF Vectorization to identify products with similar features.
"The recommendation engine is based on a weighted linear fusion scheme, where the weights are 50% for collaborative filtering for personalization, 30% for association rules for cross-selling, and 20% for content matching for diversity. Scores from each algorithm are normalized to the range [0,1] before a final recommendation is presented. For users with less purchase data, weights change dynamically; new users are recommended based on trending, and 'power users' with highly correlated orders receive collaborative filtering-driven recommendations."
3.1.4. Database: JSON Storage
The system mainly uses a JSON file–based storage approach as its database, and it is organized into two complementary layers. The first layer is db.json, which works as the runtime database for JSON Server. This file contains four collections: products (a product list with price, stock, and description information), orders (order history with payment and delivery status), users (user accounts), and reviews (if users leave product ratings, these can be used by the TimeAwareRecommender module). Any CRUD updates made through the JSON Server API are written back to this file, so the data is still available after the server restarts.
The second layer consists of dedicated JSON files stored in the data folder and managed by the Data Manager (dataManager.js). This dataset includes: products.json (product data synchronized from the runtime db.json), orders.json (structured order history), users.json (managed user data), and auditLogs.json (audit logs that record all changes made by users/admins, including timestamps, the person who performed the action, the action details, and related metadata).
This JSON-based architecture is convenient for fast development, easy setup, and offline testing. However, it is more suitable for small to medium datasets and systems with low concurrency requirements. 
3.2. Proposed Algorithms 
The Recommended Page employs a hybrid recommendation system that combines three complementary machine learning techniques to generate personalized product recommendations:
Collaborative Filtering via Matrix Factorization (50%)
Association Rule Mining via Apriori Algorithm (30%)
Content-Based Filtering (20%)



Design Rationale:
Matrix Factorization (50%): Primary algorithm for capturing latent user preferences and item characteristics through collaborative patterns.
Apriori (30%): Discovers "Frequently Bought Together" patterns for cross-selling opportunities.
Content-Based (20%): Provides diversity and handles cold-start scenarios through product feature similarity.

 3.2.2 Algorithm 2: Association Rule Mining via Apriori
3.2.2.1 Theoretical Foundation
Association Rule Mining discovers co-occurrence patterns in transactional data. The Apriori algorithm identifies itemsets that frequently appear together and generates rules of the form:
Temporal Weighted Support:
X⇒Y
Interpreted as: "Customers who buy X are likely to also buy Y"
Key Concepts:
Itemset: A collection of one or more items 
Example: {Milk,Bread}
Transaction: A set of items purchased together Example: 
T1={Milk,Bread,Butter}
Transaction Database: Collection of all transactions 
D={T1,T2,...,Tn​}
3.2.2.2 Support, Confidence, and Lift
Support: Frequency of itemset in database

Confidence: Conditional probability of Y given X

Lift: Correlation strength (independence measure)

Interpretation:
Lift = 1: X and Y are independent (no correlation)
Lift > 1: Positive correlation (X and Y appear together more than expected)
Lift < 1: Negative correlation (X and Y appear together less than expected)
3.2.2.3 Apriori Algorithm
Principle: If an itemset is frequent, then all of its subsets must also be frequent (Apriori property).
Algorithm Steps:
Input:
Transaction database D
Minimum support threshold σmin
Minimum confidence threshold cmin
Output:
Set of association rules R
Step 1: Find Frequent Itemsets
L_1 = {frequent 1-itemsets}  // Items with support >= sigma_min
k = 2
while L_{k-1} is not empty:
    C_k = apriori_gen(L_{k-1})  // Generate candidate k-itemsets
    for each transaction T in D:
        for each candidate c in C_k:
            if c is subset of T:
                c.count++
    L_k = {c in C_k : c.support >= sigma_min}  // Prune infrequent
    k++
return L = union of all L_k  // All frequent itemsets
Step 2: Generate Association Rules
for each frequent itemset l in L, |l| >= 2:
	for each non-empty subset s of l:
    	rule = s => (l - s)
    	confidence = support(l) / support(s)
    	lift = support(l) / (support(s) * support(l - s))
    	if confidence >= c_min and lift >= lift_min:
        	add rule to R
return R
